Identifies users who bring the most followers and have the highest viral potential.

Metrics Explained:
Influence Score Weighted score: (helpers × 2) + (retention% × 1.5) + (secondary referrals × 3)
Helpers Number of users who followed via this user's referral
2nd Gen Secondary referrals - helpers who also became participants and brought their own helpers
Viral K Viral coefficient: New users brought / Original users. K > 1 means exponential growth
Retention Percentage of helpers still following the OA
Trend 📈 Growing, ➡️ Stable, 📉 Declining (based on last 7 days)
Use Cases:
  • Identify power users for special rewards or partnerships

  • Target high-potential users for VIP campaigns

🔄 How Campaign Fission Works (Step-by-Step) ▼
1
User A Joins Campaign

User registers and becomes a participant. System generates a unique referral_code (e.g., CMSFJE).

Database: campaign_participants → new row with user_id, campaign_id, referral_code
2
Generate QR Code with Scene

User generates a poster with QR code. The QR embeds a scene string:

Format: camp_{campaignId}_ref_{referralCode}
Example: camp_a570fa29_ref_CMSFJE
3
User B Scans QR Code

User B scans the QR code with WeChat. WeChat sends a webhook to your server:

Event: subscribe (new follower) or SCAN (existing follower)
Contains: EventKey with scene string
4
Backend Processes Webhook

Server parses scene string, finds User A by referral_code, records helper:

Actions:
• campaign_helpers → new row linking User B to User A
• campaign_participants → increment User A's helper_count
5
Auto-Reply Sent

Server sends auto-reply message to User B with Mini Program link.

Link: pages/campaign/index?id={campaignId}&ref={referralCode}
6
User A Claims Reward

When User A reaches required helpers, they can claim rewards:

Validation: System re-validates is_valid helpers before allowing claim
Database: campaign_reward_claims → new row

🔄 实时日志工作原理 ▼
Technology: Server-Sent Events (SSE)

Live Logs uses Server-Sent Events (SSE) to push real-time events from the backend to your browser. Unlike polling (which repeatedly asks "any new events?"), SSE maintains a persistent connection and the server pushes events as they happen.

┌─────────────────┐     SSE Connection      ┌─────────────────┐
│  Admin Browser  │ ◄────────────────────── │  Backend Server │
│  (EventSource)  │     Real-time events    │  (SSE Manager)  │
└─────────────────┘                         └─────────────────┘
                                                    ▲
                                                    │
                                            broadcastEvent()
                                                    │
                            ┌───────────────────────┼───────────────────────┐
                            │                       │                       │
                     WeChat Webhook          User Actions           Campaign Events
                     (subscribe/scan)        (login/register)       (helper recorded)
Key Features:
  • Instant delivery - Events appear within milliseconds of occurring
  • No refresh needed - The page updates automatically
  • Buffer system - Last 100 events are kept in memory
  • Auto-reconnect - If connection drops, it reconnects automatically
📋 When to Use Live Logs ▼
✅ Good Use Cases
  • Testing webhooks - Watch events arrive as you scan QR codes
  • Debugging in real-time - See exactly what's happening right now
  • Demos - Show stakeholders the system working live
  • Monitoring launches - Watch a new campaign's first interactions
  • Verifying setup - Confirm webhook is receiving events
❌ Use Event History Instead
  • Searching past events - Live Logs has no search
  • Investigating issues - Event History has filters and details
  • Generating reports - Use Analytics or Event History
  • Reviewing specific users - Event History can filter by user

🎮 Controls Guide ▼
⏸️
Pause/Resume

Temporarily stop updating the display. Events are still received but not shown until you resume. Useful when you want to examine a specific event.

🗑️
Clear

Remove all events from the display. The connection stays active and new events will appear. Useful to start fresh when testing.

🔄
Reconnect

Close and re-establish the SSE connection. Use this if you see "Disconnected" status or events stop appearing.

🔴
Connection Status

Shows whether you're connected to the event stream. Green = connected, Red = disconnected, Yellow = connecting.

📲 小程序开发配置指南

本指南解释了小程序开发中 localhost 与真机测试的核心问题，以及我们的解决方案。

🔴 核心问题

为什么小程序真机无法直接访问 localhost？

  • localhost 是本地回环地址 — 指向设备自身，不是你的电脑
  • 手机和电脑是不同设备 — 手机的 localhost 是手机本身，无法到达你电脑的服务
  • 微信小程序限制 — 正式环境必须使用 HTTPS 且域名需备案

✅ 我们的解决方案

🌐

Cloudflare Tunnel + Supabase 自动同步

我们使用 Cloudflare Tunnel 将本地服务暴露到公网，并将 Tunnel URL 存储在 Supabase。 小程序启动时自动从 Supabase 获取最新 URL，无需每次手动修改代码。

工作流程：
┌──────────────┐    ┌─────────────────┐    ┌──────────────┐
│   你的电脑    │───▶│ Cloudflare Tunnel│───▶│   公网 URL   │
│ localhost:3000│    │                 │    │ xxx.trycloudflare.com │
└──────────────┘    └─────────────────┘    └──────────────┘
                                                   │
                           ┌───────────────────────┘
                           ▼
            ┌──────────────────────────┐
            │       Supabase          │◀─── Admin 后台保存 URL
            │   tunnel_config 表      │
            └──────────────────────────┘
                           │
                           ▼
            ┌──────────────────────────┐
            │      小程序 (真机)        │◀─── 启动时自动获取 URL

            └──────────────────────────┘

  1. 启动后端服务 — cd backend && npm run dev
  2. 启动 Cloudflare Tunnel — cloudflared tunnel --url http://localhost:3000
  3. 复制 Tunnel URL — 从终端输出中复制 https://xxx.trycloudflare.com
  4. 在 Admin 后台保存 URL — 「基础设施 → 隧道配置」粘贴并保存

🔧 常见问题排查

真机提示「request:fail url not in domain list」

原因：Supabase 域名未添加到合法域名列表

解决：在微信公众平台添加 https://fseyfnuqxvrcwrpshxyv.supabase.co 到 request 合法域名

真机请求超时或无响应

可能原因：

  • Cloudflare Tunnel 已断开（每次重启电脑后需要重新启动）
  • Admin 后台的 Tunnel URL 未更新
  • 后端服务未启动

解决：重新启动 tunnel 并更新 URL

模拟器正常但真机报错

原因：模拟器使用 localhost，真机需要公网 URL

解决：确保 Tunnel 正在运行且 URL 已保存到 Admin 后台

小程序无法获取 Tunnel URL

检查步骤：

  1. 确认 Supabase 域名已添加到 request 合法域名
  2. 检查 tunnel_config 表中是否有记录
  3. 清除小程序本地存储后重试

🚀 生产环境注意事项

上线生产环境前，需要完成以下配置：

  • 关闭调试开关 — 小程序代码中移除开发时的调试代码

🔗 Why Do You Need a Tunnel?

▼

WeChat Official Account needs to send real-time notifications (like user follows, unfollows, and QR scans) to your backend server. However, your local development server (localhost:3000) is not accessible from the internet.

👤 User scans QR
→
💬 WeChat Server
→
🚇 Cloudflare Tunnel
→
💻 Your localhost:3000
✅
What Cloudflare Tunnel does:

Creates a secure, public URL (like https://abc-xyz.trycloudflare.com) that forwards all requests to your local server. No need to deploy to production for testing!

⚙️
How it works:

When WeChat sends a webhook to your tunnel URL, Cloudflare securely routes it through their network to your local machine. Your backend receives the event and can process it immediately.

🔄
Important:

The tunnel URL changes each time you restart cloudflared. You must update the webhook URL in WeChat OA backend whenever this happens.

📱 Why Do You Need WeChat Official Account?

▼

WeChat Official Account is essential for receiving user interactions like follows, unfollows, and QR code scans. It allows your backend to track user engagement and trigger campaign logic automatically.

🔄
Data Flow:

User Scan → WeChat Server → Webhook (via Tunnel) → Backend → Database

📦
Data Storage:

.env file: OA_APPID, OA_SECRET, OA_TOKEN, OA_ENCODING_AES_KEY

Database tables: oa_qrcodes, oa_scan_events, oa_follow_events, campaign_helpers

🚀
Production Migration:
  1. Update Webhook URL to production server in WeChat OA backend
  2. Set environment variables with production values
  3. Add production server IP to WeChat IP whitelist (if required)
  4. Test webhook events in production

Quick Reference

▼
Get AppID & Secret

WeChat Official Account Platform → Development → Basic Configuration

Configure Webhook

WeChat OA Platform → Basic Configuration → Server Configuration → Set your tunnel URL + /api/oa/webhook

Generate Encoding AES Key

Click "Generate" button in WeChat OA Platform → Basic Configuration

🗄️ Why Do You Need Database?

▼

Supabase (PostgreSQL) stores all your application data including users, campaigns, referrals, and event logs. It's the central data repository for your viral marketing system.

🔄
Data Flow:

Backend Server → Supabase Client → PostgreSQL Database

📦
Data Storage:

.env file: SUPABASE_URL, SUPABASE_KEY

Key tables: users, campaigns, campaign_participants, campaign_helpers, campaign_rewards, event_logs

🚀
Production Migration:
  1. Create production Supabase project
  2. Run all database migrations (in database/migrations/)
  3. Update environment variables with production Supabase credentials
  4. Configure database connection pool settings
  5. Set up automated backups
  6. Migrate existing data if needed

Quick Reference

▼
Get Supabase URL & Key

Supabase Dashboard → Project Settings → API

Run Migrations
psql -h your-db-url -f migrations/XXX.sql
View Database Logs

Supabase Dashboard → Logs → Database

💻 Why Do You Need Backend Server?

▼

Backend Server handles all business logic, API requests, database operations, and WeChat event processing. It's the brain of your viral marketing system.

🔄
Data Flow:

Mini Program/OA → Backend Server → Database

External Services → Cloudflare Tunnel → Backend Server

📦
Data Storage:

Code: backend/src/ directory

Environment: .env file

Logs: Console output + event_logs table

Config: backend/src/config/

🚀
Production Migration:
  1. Deploy to production server (Vercel, Railway, AWS, etc.)
  2. Set production environment variables
  3. Configure domain and SSL certificate
  4. Set NODE_ENV=production
  5. Configure log collection (optional)
  6. Set up monitoring and alerts
  7. Configure auto-restart (e.g., PM2)

Quick Reference

▼
Start Server
cd backend && npm run dev
View Server Logs
tail -f backend/logs/app.log
Check Server Process

Stop Server
lsof -ti:3000 | xargs kill -9

🔄
Unfollow Handling (Balanced Approach):
  1. When user unfollows: Set is_valid = false in campaign_helpers
  2. Don't immediately update participant's helper_count
  3. On reward claim: Re-calculate valid helpers only
  4. If insufficient: Show "Some helpers unfollowed, need X more"
  5. If re-follows: Restore is_valid = true
🚫
Duplicate Prevention:

Same user (by openid) can only help once per participant per campaign

Database unique constraint: (helper_openid, participant_id, campaign_id)

⏰
Time Limits:

Campaign has start_date and end_date

Helpers only count if within campaign period

🔍
Admin Monitoring:

Real-time event stream shows suspicious patterns

Filter by: rapid helps from same IP, bot-like behavior

Why Do You Need a Tunnel?

            

            

              

                WeChat Official Account needs to send real-time notifications (like user follows, unfollows, and QR scans) to your backend server. However, your local development server (localhost:3000) is not accessible from the internet.
              

              
              

                

                  

                    👤
                    User scans QR
                  

                  
→

                  

                    💬
                    WeChat Server
                  

                  
→

                  

                    🚇
                    Cloudflare Tunnel
                  

                  
→

                  

                    💻
                    Your localhost:3000
                  

                

              


              

                

                  ✅
                  

                    What Cloudflare Tunnel does:
                    
Creates a secure, public URL (like https://abc-xyz.trycloudflare.com) that forwards all requests to your local server. No need to deploy to production for testing!

                  

                

                

                  ⚙️
                  

                    How it works:
                    
When WeChat sends a webhook to your tunnel URL, Cloudflare securely routes it through their network to your local machine. Your backend receives the event and can process it immediately.

                  

                

                

                  🔄
                  

                    Important:
                    
The tunnel URL changes each time you restart cloudflared. You must update the webhook URL in WeChat OA backend whenever this happens.
